# 采集周期漂移与修复（2026-09-08 13:1x UTC）

## 1. 由就绪度面板发现

RH-08b 的 `stage_a_status` 用**计划应观测窗口**作覆盖率分母（PRD §21.1 明令，不得删掉坏窗口后报 100%）。首次用真实数据跑就暴露问题：

```
实测: 7.9957h / 72h   样本 1726 / 应有 1919
覆盖率 = 0.8994        passed = False
blockers = ['HOURS_COVERED_INSUFFICIENT', 'COVERAGE_INSUFFICIENT']
```

**覆盖率 89.9%，远低于 PRD 要求的 99%。** 若分母用「实际样本数」，覆盖率会永远是 100%，这个问题**永远不会被发现**——这正是 PRD 坚持该分母定义的原因。

## 2. 诊断：不是断档，是每轮系统性多花 1.4 秒

| 指标 | 值 |
|---|---|
| 中位间隔 | **16.4s**（目标 15.0s） |
| 均值间隔 | 16.7s |
| 间隔 >60s 的断档 | 仅 **4 次**，共约 4.4 分钟 |
| 累计缺失 | 48.5 分钟 ≈ 194 个样本 |

断档只占缺口的一小部分，**主因是每轮固定多出 ~1.4 秒**。

单轮成本：5 次串行 `eth_call`，单次延迟中位数 292ms、p95 585ms → 每轮约 **1.5 秒**。

## 3. 根因：sleep 从「本轮结束」而非「本轮开始」计时

```python
# 修复前
delay = sleep_for + backoff
slept = 0.0
while slept < delay:          # 采集耗时 1.5s 之后，再睡满 15s
    time.sleep(min(1.0, delay - slept))
    slept += 1.0
```

实际周期 = 采集耗时 + sleep = 1.5 + 15 = **16.5 秒**，与实测 16.4 秒吻合。误差按比例累积：每小时丢约 5.5 分钟，8 小时丢 44 分钟。

## 4. 修复：按截止时刻睡眠

```python
round_started = time.monotonic()      # 每轮开始时记录
...
deadline = round_started + delay      # 截止时刻从"开始"算
while not _STOP["flag"]:
    remaining = deadline - time.monotonic()
    if remaining <= 0: break
    time.sleep(min(1.0, remaining))
```

用 `time.monotonic()` 而非 `time.time()`，避免系统时钟调整（B1 §10.7 记录过本机时钟曾偏移 3 天）影响周期。

## 5. 验证

重启前样本 1730。优雅 SIGTERM 退出，新进程 PPID=1。重启后最近四个间隔：

```
[12.4, 15.0, 15.0, 15.0]   目标 15.0s
```

首个 12.4s 是重启衔接，之后**精确 15.0 秒**。13 个配对测试全绿。

## 6. 对 Stage A 计时的影响

**已积累的 8 小时观测数据仍然有效**——价格、区块、RPC 健康都是真实采样，只是密度略低于计划。但**覆盖率 89.9% 不满足 PRD §21.1 的 99% 门槛**。

处置（严格按 PRD，不自欺）：

1. **不重置 Stage A 计时**：观测起点仍是 05:15:14Z，已覆盖时长照常累计。
2. **覆盖率按真实值报告**，不因「已修复」而追溯调高。
3. 修复后新增样本的间隔为 15.0s，**覆盖率会随时间自然回升**；72 小时到期时若整体覆盖率仍 <99%，按 PRD §21.1「未达到覆盖要求时可继续采集，但不毕业」处理——**延长观测，不放宽门槛**。
4. 该缺口已写入 `READINESS_DASHBOARD` 的 blockers，任何毕业判定都会看到它。
