# 换腿成本高估 940 倍：撤回上午的经济判定（2026-09-08 13:5x UTC）

## 1. 必须先说的结论

**2026-09-08 12:2x 提交的 `RH-04b/FIRST_CLOSED_LOOP.md` 中「该池 NetCover ≈ 0.028，经济上不可行」的判定，现予撤回。** 该结论建立在一个被高估 940 倍的成本输入上。修复后同一池、同一实测费率下 **NetCover = 2.79，过闸**。

## 2. 这个 bug 是被自己写的测试抓出来的

RH-04d 的 spec 里预设了一条自我拆穿：`fixed_cost_share` 在三个仓位上测固定成本，**若成本随仓位线性增长，测试必须如实失败并指出「成本模型可能把全额本金当换腿额」**，明令不许为了让测试过而放宽。

worker 交付后该测试**如实失败**：

```
AssertionError: 成本模型可能把全额本金当换腿额 (PRD §11.3):
fixed cost grows with position size (max pairwise relative diff = 5513.64)
```

实测固定成本占仓位比例：$50 → 18.85%，$500 → 187.96%，$5000 → **1039.70%**。成本超过本金十倍，显然荒谬。

## 3. 根因：`price` 参数未按精度归一

`scripts/lp_rh_netcover_inputs_v1_readonly.py` 原第 115 行：

```python
price = (sqrt_price_x96 / 2.0 ** 96) ** 2      # RAW token1/token0 比值
```

`sqrtPriceX96²` 是**原始比值** `2.49e-9`，而成本模型期望的是**按 decimals 归一后的价格** `2490.58`。对 18/6 精度对，两者相差 **10¹²**。

底层成本模型本身完全正确——直接调用它，5 万美元换腿只收 9.71 美元（占 0.019%）：

| 仓位 | 用 raw price | 用归一 price | 高估倍数 |
|---:|---:|---:|---:|
| $50 | $4.7034 | $0.0050 | **940×** |
| $500 | $469.89 | $0.0505 | 930× |
| $5,000 | $46,984.67 | $0.5470 | 859× |
| $50,000 | $4,698,422 | $9.6984 | 484× |

## 4. 修复

```python
d0, d1 = int(dec0), int(dec1)
price = ((sqrt_price_x96 / 2.0 ** 96) ** 2) * (10 ** d0) / (10 ** d1)
```

修复后固定成本占仓位比例回到 **0.02%–0.06%**，且对仓位近似恒定，与 B1 §9.5「固定成本 ≈ 2×池费档、几乎不随仓位变化」一致。同时与主脑用 661 个真实 tick 实测的退出冲击（$50,000 → 1.029 bps）量级相符。

## 5. 修复后的经济结论（实测费率 27.34%）

| 仓位 | 持有期 | fee_ev | NetCover | 过闸 |
|---:|---:|---:|---:|:--:|
| $50 | 168h | $0.262 | **2.79** | ✅ |
| $50 | 720h | $1.124 | 3.70 | ✅ |
| $500 | 168h | $2.622 | 3.45 | ✅ |
| $5,000 | 720h | $112.36 | 3.94 | ✅ |

**但这仍不是「可以开仓」的结论**，理由与上午相同且未改变：

1. 费率 27.34% 来自 **91 秒**采样窗口，PRD §21.1 要求 ≥72h。
2. 该费率是**全区间上界**，未按 in-range 时长折算。
3. 终闸十项里另外九项仍需各自证据；`capital_policy_pass` 在 LIVE 下仍是 `CAPITAL_POLICY_CONFLICT`。
4. `usable_provider_count = 1`，LIVE 闸按 §8.3 保持 BLOCKED。

**正确表述**：此前的「不可行」判定源于计算错误已撤回；当前证据只支持「该池在修复后的成本模型下 NetCover 为正」，**不支持任何开仓决定**。

## 6. 这是今天第五个「精度类静默错误」

| # | 陷阱 | 表现 |
|---|---|---|
| 1 | USDG 6 位小数 | 292 个 USDG 池价格全错，75 个 WETH 池正常 |
| 2 | `liquidityNet` int128 按 256 位符号扩展 | 错误解码得 1.157e77，退出深度变「无限」 |
| 3 | 池 token 顺序不固定 | 同精度池只返回倒数，量级正常方向错误 |
| 4 | `_state_factors` 默认 decimals=0/price=1 | $50,000 当成 50,000 wei，退出深度算成 0 |
| 5 | **本条：raw ratio 当归一价格** | 换腿成本高估 940 倍，把可行池判成不可行 |

**五个全都不抛异常。** 第 5 条尤其危险：前四条会给出荒谬值（易发现），这条给出的 $4.70 看起来**完全合理**——直到在三个仓位规模上对比才露馅。

**教训**：任何跨精度边界的数值传递都必须有**跨规模一致性测试**。单点验证无法发现比例错误。

## 7. 全库排查结论（2026-09-08 14:1x）

修复装配器后立即 grep 全部 `sqrtPriceX96` 算术，**发现第二处同款 bug**：

- `scripts/lp_rh_horizon_sweep_v1_readonly.py:57` 的 `_pool_params` 同样把 raw ratio 直接当价格传给成本模型，且其 docstring 也写着错误公式。已修复，并更正 docstring 以免后人照抄。

**值得记录的是它为何没被测试抓到**：`horizon_sweep` 的 16 个测试在修复前后**都通过**，因为它们比较的全是同一价格标度内的形状与比值，而**一个均匀的 1e12 误差在比值里会约掉**。只有读代码才能发现。

### 其余调用点全部合规

跨行扫描 `scripts/*.py` 中所有 `(sqrtPriceX96 / 2**96)**2` 与 `ratio*ratio` 写法，逐个检查其后 3 行内是否有精度缩放：

| 文件 | 结论 |
|---|---|
| `lp_tier_c_exit_feasibility_v1_readonly.py:82` | 下一行 `* (10 ** (dec0 - dec1))` ✓ |
| `lp_tier_b_level2_replay_v1_readonly.py:32` | 下一行 `* (10.0 ** (dec0 - dec1))` ✓ |
| `lp_il_math_replay_v1_readonly.py:93` | 下一行 `* 10 ** (18 - 6)` ✓ |
| `lp_netcover_inputs_v1_readonly.py:469` | 同行含缩放 ✓ |
| `strategy_pivot_d2/d4`、`strategy_evidence_r4b/r4c` | 仅定义 `Q96` 常量或 tick→sqrtPrice 转换，不涉及价格换算 ✓ |

**结论：全库仅 RH 支线新增的两处有此缺陷，旧链模块（B1 时期）全部正确。** 这说明该错误是本次 RH 开发引入的新债，不是继承来的。

### 对 RH-09a 的要求

正在开发的跨规模审计工具必须能同时抓住这两处的形态——静态扫描要能识别「平方后 N 行内无精度缩放」，且要在真实仓库上回归验证**修复后不再报警**。
