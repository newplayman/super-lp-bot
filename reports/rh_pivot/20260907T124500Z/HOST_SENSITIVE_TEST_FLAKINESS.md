# 宿主敏感测试的并发误报（2026-09-08 记录）

## 现象

全量 `pytest` 在**有 worker 并发运行时**会出现不稳定失败：

| 时间 | 失败数 | 并发情况 | 复跑结果 |
|---|---|---|---|
| 09:5x | 1 | codex 4 路 | 连跑 3 次全绿（3449） |
| 11:4x | **19** | qwen 2 路 + codex 3 进程 | 连跑 3 次全绿（3509） |

失败数与并发进程数正相关。

## 根因

B1 §10.4 已记录该形态：`tests/test_p0_postgres_shadow_audit_v1.py::test_safety_no_forbidden_process` 等测试**扫描全机 `ps aux`**，查找 `private_key` / `mnemonic` / `sendTransaction` / `canary` 等关键词，**任何进程的命令行含这些词即判失败**。

RH 转向期间的 worker 命令行里带着 spec 路径与提示词，其中包含 `private_key`、`send_raw`、`sendTransaction` 等**作为禁用项被写进 spec 的字符串**——例如 RH-07a 的 spec 明确要求「源码断言不含 `import web3`、`eth_account`、`sign`、`send_raw`、`private_key`」。这些词出现在 worker 的命令行里，就把宿主扫描测试打挂了。

**这是审计命令自身触发的误报**，B1 §10.4 原文：「宿主敏感进程扫描测试可能被审计命令自身触发，应保存完整现场、在无冲突环境复测」。

## 处理原则（严格遵守 PRD §20 与 B1 §11）

1. **不得把这些测试加入白名单**，不得削弱其断言——它们防的是真实的私钥/广播进程泄漏。
2. **不得因为"是误报"就跳过**。每次出现都必须在**无并发**环境复跑确认，并记录两次结果。
3. 复跑仍失败 → 视为真实退化，按 PRD §20 处理。
4. 判定标准：失败集合是否**只**包含扫描宿主进程的那几个测试。若含其它测试，不适用本条。

## 本次两起的处置

- 11:4x 的 19 个失败：无并发复跑 3 次全绿（3509 passed / 14 skipped）→ 判误报，本文件记录。

**两次都没有跳过、没有加白名单、没有改测试。**
