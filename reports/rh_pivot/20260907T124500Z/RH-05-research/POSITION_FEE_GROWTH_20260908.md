# 头寸级 fee-growth 回放（2026-09-08 09:1x UTC，主脑亲跑）

## 1. 为什么不能用之前那个数

08:0x 那次测算是「全池成交额 × 费档」，得到 USDG/WETH 池 8.4 分钟收 125.80 美元。PRD §11.2 明令：**不能按 TVL 占比直接乘全池 volume 得出精确收益**。本次改用 Uniswap V3 的正规口径。

## 2. 方法：`feeGrowthGlobal` 增量

V3 用 Q128.128 定点累加器记录「每单位流动性累计应得的费用」。某头寸在一段时间内的应计费用为

```
fee_token = L_position × Δ(feeGrowthGlobal_token) / 2^128
```

这是**协议自己的记账口径**，不是外部估算。实测两次采样：

| 项 | 值 |
|---|---|
| 起始区块 | 57,576,525 |
| 结束区块 | 57,577,419（**+894 区块 / 91 秒**） |
| 当前 tick | −198,161 |
| 活跃流动性 | 9,655,235,318,856,690,467 |
| `Δ feeGrowthGlobal0X128` | 140,852,024,524,429,674,789,730,399,812,314,206 |
| `Δ feeGrowthGlobal1X128` | 535,492,293,412,818,417,209,831,991 |

## 5. 仍然不能当收益结论的四条

1. **窗口 91 秒**。PRD §21.1 要求 ≥72h。当前 Stage A 才 4 小时。
2. **这是全区间头寸的上界**。集中流动性头寸只在价格落在其区间内时计费，实际收益要按 **in-range 时长**折算。区间越窄、单位流动性费率越高，但 out-of-range 时收益为 0。
3. **一项成本未扣**。gas、换腿、滑点、IL、逆向选择全部未计。PRD §11.3 的全成本清单一条都没算。
4. **未验证有机性**。894 个区块里的成交可能含刷量，PRD §10.3 要求区分 raw 与 organic。

## 6. 对 RH-04b Shadow Runner 的直接输入

`feeGrowthGlobal` 增量是 Shadow 账本计算 `accrued_fees` 的**正确数据源**。Shadow runner 应当：

1. 每个采样点记录 `feeGrowthGlobal0X128` / `feeGrowthGlobal1X128`；
2. 对每个虚拟头寸按 `L × Δfee_growth / 2^128` 累加，**而不是**按 TVL 占比分摊；
3. 集中流动性头寸还需 `ticks(lower/upper).feeGrowthOutside` 来算区间内的 fee-growth，本次未采（全区间近似已足够作 CORE 首版）；
4. 采样间隔内价格若跑出区间，该段计 0。
