# 第二 RPC 提供方核验：LIVE 闸的单点阻塞已解除（2026-09-08 14:5x UTC，主脑亲跑）

## 结论（2026-09-08 16:0x UTC **全面撤回并重写**，见文末更正 3）

**本报告初版称「usable_provider_count = 3，PRD §8.3 该项 PASS，LIVE 单点阻塞解除」。
这个结论现予撤回。** 按 PRD §8.3 的**完整能力清单**复测，**没有一个提供方全部通过**，
`usable_provider_count = 0`。LIVE 的单点数据源阻塞**依然存在**。

撤回的三条理由，逐条在文末展开：
1. `usable_provider_count >= 2` 这个阈值**不是 PRD 的原文**，是本仓
   `scripts/lp_rh_readiness_v1_readonly.py:118` 自定的实现。PRD §8.3 的原话是
   「READONLY 可暂用公开单点；**LIVE 不允许该单点成为唯一可用数据源**」。
2. PRD §8.3 要求实测的能力是 **chainId、block/hash 一致性、历史读取、日志范围、
   eth_call、gas estimate、WS（可选）、错误结构**。我初版只测了其中 5 项，
   **漏测了「历史读取」与「日志范围」这两项**——而恰恰是这两项把三家全部拦下。
3. 初版把 `eth_getLogs` 的单区块查询成功当作该能力通过。**带区间的日志查询是另一回事。**

## 来源不是猜的

端点取自 ethereum-lists 官方链注册表 `chainid.network/chains.json` 中 chainId 4663
（`Robinhood Chain`，原生币 ETH）的 `rpc` 字段，不是我拼凑的域名。

## 逐方法核验（PRD §8.3 要求按方法而非按提供方判定）

固定在同一区块 **57774374**（当前高度回退 30 块，确保各方都已同步）以便结果可比。

| 提供方 | chainId | blockNumber | eth_call | getBlockByNumber | eth_getLogs | 判定 |
|---|---|---|---|---|---|---|
| `rpc.mainnet.chain.robinhood.com` | 284ms | 265ms | 291ms | 291ms | 515ms | 可用 |
| `robinhood-rpc.publicnode.com` | 100ms | 88ms | 113ms | 105ms | 91ms | 可用（最快） |
| `rpc.ordofi.network` | 232ms | 207ms | 259ms | 474ms | 239ms | 可用 |
| `rpc.arrowrpc.com` | FAIL | FAIL | FAIL | FAIL | FAIL | **不可用**（HTTP 530，全方法） |

`eth_call` 用的是 SGOV/USDG fee-3000 池的 `slot0()`，即本项目真实会打的调用，不是空探针。

## 一致性：固定区块上无 SOURCE_DISAGREEMENT

同一固定区块 57774374 上，三个可用提供方对 `eth_chainId` / `eth_call` /
`eth_getBlockByNumber` / `eth_getLogs` 的返回 **sha256 摘要逐字节一致**。按 PRD §9.3，
不一致本应触发 `SOURCE_DISAGREEMENT` 并禁止新仓；本次未触发。

### 更正：`eth_blockNumber` 三家不一致，但那不是分歧

初稿把 `eth_blockNumber` 也算进「五个方法逐字节一致」，**这是错的**。该方法返回各家
自己的链头，本来就该不同。实测三轮并列取样：

| 轮次 | primary | publicnode | ordofi | 极差 |
|---|---|---|---|---|
| 1 | 57775042 | 57775048 | 57775050 | 8 块 |
| 2 | 57775087 | 57775094 | 57775097 | 10 块 |
| 3 | 57775132 | 57775185 | 57775186 | 54 块 |

**由此得到一条本来不在预期内的发现：我们正在用的主端点
`rpc.mainnet.chain.robinhood.com` 每一轮都是三家里最落后的**，落后 6 到 54 块；
而 `publicnode` 既最快（88–113ms，主端点是 265–291ms）又最接近链头。

两条实现要求：

1. **一致性比对只能在固定区块上做。** 拿 `eth_blockNumber` 去比对会把正常的同步延迟
   误报成 `SOURCE_DISAGREEMENT`，从而无谓地禁掉新仓。RH-01d 的 `detect_disagreement`
   只对显式传入的 `consensus_methods` 生效，正是为此。
2. **链头落后已量化，结论是不重要——但过程值得记下。**
   我起初把「落后 54 块」当成时效性风险写进了报告。随后实测出块间隔：
   **0.102 秒/块**（1000 块跨 102 秒）。于是

   | 量 | 块数 | 折合时间 |
   |---|---|---|
   | 主端点落后（6 次取样中位） | 9 块 | **0.9 s** |
   | 主端点落后（本次最大） | 12 块 | 1.2 s |
   | 先前观察到的瞬时极差 | 54 块 | 5.5 s |
   | 参考价自身报价龄（REST `generatedAt`） | — | **15–20 s** |

   主端点确实每轮都最落后，但折合 **0.9 秒**，比参考价自身的报价龄**小一个数量级**。
   链价与参考价之间的时序错配由 REST 那一侧主导，换 RPC 提供方**解决不了**它。

   **教训：块数不是时间。** 在一条 0.1 秒出块的链上按块数直觉判断时效性会把
   一个可忽略量报成风险。任何以块为单位的时效断言，必须先乘出块间隔再下结论。

## 这条证据的边界（不得夸大）

1. **这是一次时点快照，不是可用性序列。** 三个提供方此刻全通，不等于观测窗口内持续可用。
   `arrowrpc` 恰好证明注册表里的端点会挂。持续可用性需要把它们接进轮循池后按周期记录，
   这正是 RH-01d（`lp_rh_provider_pool_v1_readonly`）在建的东西。
2. **一致性只在一个区块、五个方法上验证过。** 归档节点深度、日志区块跨度上限、
   速率限制各家不同，均未测。`eth_getLogs` 只查了单区块，宽区间行为未知。
3. **采集器目前仍只用主端点。** 本报告不改变任何运行中进程的配置。
4. 三家的独立性只到「不同域名与运营方」这一层；是否共用同一上游基础设施未核实。

# 更正 3（2026-09-08 16:0x UTC）：按 PRD §8.3 完整能力清单复测

## PRD §8.3 原文

> 需要实测 chainId、block/hash 一致性、**历史读取**、**日志范围**、eth_call、gas estimate、
> WS（可选）及错误结构。主／备 URL 指向同一后端不能视为两套独立证据。
> READONLY 可暂用公开单点；**LIVE 不允许该单点成为唯一可用数据源**。

## 复测结果

| 能力 | primary | publicnode | ordofi |
|---|---|---|---|
| chainId | ok | ok | ok |
| eth_call（head−30） | ok | **HTTP 403** | ok |
| **历史读取（head−2,000,000）** | **失败** | **HTTP 403** | **失败** |
| **日志范围 1,000 块** | ok | **HTTP 403** | ok |
| **日志范围 10,000 块** | **失败** | **HTTP 403** | ok |
| gas estimate | ok | ok | ok |
| block/hash 一致 | ok | ok | ok |
| 错误结构（结构化 JSON-RPC error） | ok | ok | ok |

**全能力通过者：无。`usable_provider_count = 0`。**

## 状态保留深度实测（二分搜索）

对每家做 `eth_call(slot0, blockNumber=head−N)` 二分，找最深可读的 N：

| 提供方 | 最深可读 | 折合时间 |
|---|---:|---:|
| **primary**（当前采集器在用） | head − 6,137 块 | **10.4 分钟** |
| **ordofi** | head − 1,800,100 块 | **51.0 小时** |
| publicnode | 连 head−30 都读不到 | **不支持历史查询** |

**这是本次复测最重要的发现，且与初版结论方向相反：**

1. **我们正在用的主端点，状态保留只有 10 分钟。** 任何需要回看超过 10 分钟的计算
   （费率累加器差分、对账、回补）在 primary 上**必然失败**。采集器每 15 秒读 `latest`
   所以现在没暴露问题，但 Stage B 的日对账一定会撞上。
2. **ordofi 是三家里唯一有实用历史深度的（51 小时），也是唯一稳定支持 10,000 块
   日志范围的。** 初版把它列为「可用」之一而把 primary 当默认，实际上**该反过来**。
3. publicnode 只服务 `latest`：初版测它 `eth_call` 通过，是因为我固定的区块恰好是
   head−30，落在它当时的窗口里；这次同样的调用返回 403。**它的能力是不稳定的。**

## primary 的 10,000 块日志查询是**不稳定**，不是「支持」

15:4x 时 primary 对 10,000 块的 `eth_getLogs` 返回 8,643 条（我据此完成了有机成交量测量）；
16:0x 复测同样的请求失败。**同一端点同一请求，二十分钟内从成功变失败。**
因此有机成交量那次测量能做成，一部分是运气。该结论的数据基础需要在 ordofi 上复现一次。

## 对 LIVE 闸的最终判定

PRD 的要求不是「凑够两个能连上的端点」，而是「LIVE 不允许该单点成为唯一可用数据源」。
按完整能力清单，**目前连一个全能力可用的数据源都没有**，谈不上「不再唯一」。

**`usable_provider_count` 应记为 0，LIVE 闸的这一项判定为 BLOCKED。**
本报告初版的相反结论作废。
