# RH-02bi：扫描器基线改用「内容指纹」匹配，而非行号

## 问题（今晚已两次误报）

`scripts/lp_silent_failure_lint_v1_readonly.py` 的基线
（`reports/silent_failure_lint_baseline.json`）按 **`文件:行号`** 匹配。
**编辑任何一个文件，都会让它后面所有命中整体位移，全部被判成「新增」。**

实测两次：
1. `8b69b7c` 改 `shadow_runner.py` → 11 条存量命中被判新增；
2. `bb57453` 再改同一文件 → 又是一批。

第二次尤其误导：被判「新增」的 5 条里，恰好有 `bool(sample.get("chain_degraded"))`
这个**真缺陷**（第 20 例），一眼看去像是刚引入的，实际是存量老账。

**一个天天喊狼来了的告警，很快就没人看了。** 这直接决定扫描器能不能长期用。

## 你要做的

### 一、基线条目改用内容指纹

每条命中的身份改为：

```
(相对文件路径, 规则编号, 代码片段的规范化指纹)
```

**规范化指纹**：把命中的那行（或 AST 节点对应的源码片段）
去掉首尾空白、压缩内部连续空白为单个空格，再取 `sha256` 前 16 位十六进制。
理由：缩进变化（例如被包进 `with` 块）不应算新命中——
今晚 `RH-02ax` 就把大量代码整体缩进了一级。

**行号仍要保留在基线里**，但**只作展示用**，不参与匹配。
人看报告时需要行号定位，机器判新增时不看它。

### 二、同文件同指纹出现多次的处理

同一个文件里可能有多行完全相同的代码（例如两处都写
`p0_usd = PRICES_USD.get(sym, Decimal("0"))`）。
指纹会相同 —— 用**计数**区分：基线记 `{指纹: 出现次数}`，
新增判定是「当前次数 > 基线次数」。
**在报告里说明你怎么处理的，并写一条测试锁住这个行为。**

### 三、迁移现有基线

`--write-baseline` 生成新格式。**旧格式基线要能被识别并给出清晰提示**
（例如「基线是旧格式，请重新生成」），**不要静默当成空基线**——
静默当空基线会让所有 366 条命中变成「新增」，
那正是这个项目已确认 24 例的那一族缺陷（缺数据当成某个值）。

### 四、自证有效（这是验收重点）

**必须证明「纯行号位移不再误报」**：

1. 取一个有命中的文件，复制到临时目录，**在文件开头插入 20 行注释**
   （只改行号，不改任何代码）；
2. 对原文件和改动后的文件分别扫描；
3. 断言：**两次的指纹集合完全相同**，`--fail-on-new` 不报新增。

**再证明「真新增仍能抓到」**：

4. 在那个临时文件里**加一行新的违规代码**（例如 `x = d.get("k", 0)`）；
5. 断言 `--fail-on-new` 这次**确实报新增**，且报的就是那一行。

两个自证都要写成测试，并把实际输出贴进报告。

## 不许动

`scripts/lp_rh_*`、任何 `.db`、`reports/` 下除基线文件外的任何文件。
`tests/test_lp_silent_failure_lint_v1_readonly.py` 可以改（它测的就是这个工具）。

## 验收标准

1. 上面四条自证全部通过，原样输出贴进报告。
2. 迁移后基线条目数仍是 **366**（内容没变，只是身份算法变了）。
   若数字不同，**说明差额来自哪里**（例如同指纹合并计数）。
3. `--fail-on-new` 在新基线下退出码 0。
4. 全仓扫描耗时仍 < 10 秒（贴出实测；当前是 2.42 秒）。
5. 全量 `pytest tests/ -q -p no:cacheprovider | tail -3`：
   基线 **4654 passed / 0 failed**，不得新增 failed。
